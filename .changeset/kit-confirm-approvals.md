A new confirmation mode, `MCP_CONFIRM=approvals`, has a person approve each `money` call (and each `write` its policy marks `confirm`) on their own device, through an approval service the deployment runs. Before the call runs, the server files the same one line `elicit` would show with the service, holds the call open while it waits, and runs it only on a yes, on exactly the arguments the line was written from. The question never passes through the client or the model, so it holds where the other modes do not: against a client that runs tools without asking, and against an agent that a prompt injection steers, even one holding the server's token. A no, no answer within `MCP_APPROVALS_TIMEOUT_S` (600 s by default), a service that cannot be reached, a token that cannot be read, or an answer the server cannot read all refuse the call (`confirmation_denied` or `confirmation_unavailable`) and nothing runs; a question nobody needs any more is withdrawn. While it waits the call reports progress, and a client that cancels it withdraws the question.

The service is any MCP server over Streamable HTTP that offers three tools: one that files a yes-or-no question, one that waits for its answer, one that withdraws it (docs/configuration.md, "The approval service's protocol"). `MCP_APPROVALS_URL` names it, `MCP_APPROVALS_TOKEN_FILE` holds its bearer token (read on every question), `MCP_APPROVALS_TOOLS` its tool names, and `MCP_APPROVALS_REQUESTER_META` the `_meta` key of a requester record for a service that shows who asks. Its host passes `MCP_EGRESS_ALLOW` without being listed there. A server that listens over HTTP refuses to start when the wait would not leave a call two minutes within `MCP_HTTP_TIMEOUT_MS`. Audit lines record `confirmed: "approvals"` for an approved call. The other modes are unchanged, but for one sentence: the remedy of `confirmation_unavailable` now names both reasons a server could not ask.
